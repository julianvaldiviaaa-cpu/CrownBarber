================================================================================
1. RESUMEN DEL PROYECTO
================================================================================

CrownBarber es una aplicación Laravel + Inertia React para gestionar citas de
una barbería. Permite:

- Registrar usuarios con 3 roles: cliente (user), barbero (worker) y admin.
- Al admin/barbero configurar los horarios de apertura (semanal recurrente) y
  excepciones por fecha (festivos, cierres, horarios especiales).
- Al cliente agendar una cita en 3 pasos: elige servicios -> día/hora ->
  barbero. Solo se muestran las horas realmente libres del barbero.
- Al barbero confirmar o rechazar una solicitud, o proponer una hora
  alternativa (negociación entre las dos partes).
- Notificaciones dentro de la app (campanita) para cada cambio de estado.
- Paneles por rol: dashboard del cliente, del barbero y del admin (con
  estadísticas generales del negocio).

El flujo de "Web Push" (notificaciones del navegador mediante service worker +
suscripción VAPID) se llegó a implementar parcialmente, pero POR DECISIÓN DEL
USUARIO se eliminó por completo: se quitó el paquete minishlink/web-push, la
configuración, el channel/message, el modelo push_subscriptions, el service
worker, el hook de suscripción y las llaves VAPID. Las notificaciones en app
(canal database + campanita) se mantienen y son el canal definitivo.

3. DECISIONES DE DISEÑO
================================================================================

1. ROLES: enum App\UserRoles { Admin='admin', Worker='worker', User='user' }.
   - "user" (cliente) solo agenda.
   - "worker" y "admin" ejercen de barbero en el sistema de citas.
   - Un admin también puede ser barbero: ve sus citas asignadas como tal.

2. AGENDA: solo el rol "user" crea citas. El barbero (worker/admin) nunca crea
   citas; administra las solicitudes que le llegan.

3. HORARIOS:
   - BusinessHour: horario semanal recurrente (día de semana -> open/close).
   - BusinessHourOverride: excepción por fecha concreta (cerrado o con horario
     especial). SIEMPRE tiene prioridad sobre el semanal.
   - Los slots se generan cada 30 minutos y solo se ofrecen horas libres del
     barbero (sin conflicto con otras citas activas).

4. NEGOCIACIÓN DE HORA:
   - Estado inicial de una cita: pending.
   - El barbero puede confirmarla (confirmed), rechazarla (cancelled) o
     proponer otra hora (proposed + proposed_starts_at + proposed_by).
   - En estado proposed, el usuario puede confirmar (se toma la hora propuesta),
     rechazar, o proponer a su vez otra hora. La negociación puede alternar.
   - Solo se puede proponer/cancelar en estados pending/proposed.
   - La cita confirmada y futura puede ser cancelada por cualquiera de las dos
     partes.

5. SNAPSHOT DE SERVICIOS: al crear la cita se copia en la tabla pivote
   appointment_services el nombre y precio de cada servicio en ese momento, de
   modo que el historial no cambia si el admin edita el catálogo.

6. NOTIFICACIONES: canal "database" (tabla notifications). Cada notificación
   guarda appointment_id, type, message, starts_at (hora efectiva), actor_name
   y url. El frontend hace polling cada ~30s contra notifications.latest y
   recarga los props de Inertia (compartidos en HandleInertiaRequests) para
   actualizar la campanita.

7. WEB PUSH: ELIMINADO por decisión del usuario (ver sección 9).

5.3 SERVICIO DE NEGOCIO (clave)
--------------------------------------------------------------------------------
app/Services/BusinessHoursService.php

    SLOT_INTERVAL_MINUTES = 30

    hoursForDate(Carbon $date): ?array
        - Busca BusinessHourOverride::forDate($date).
          - Si existe y está cerrado o no tiene open/close -> null (cerrado).
          - Si existe -> ventana [open, close] del override.
        - Si no hay override -> BusinessHour::forDate($date); si no hay horario
          semanal activo -> null.
        - Devuelve ['open' => Carbon, 'close' => Carbon].

    isWithinHours(Carbon $startsAt, int $durationMinutes): bool
        - Comprueba que [startsAt, startsAt+duration] quepa en la ventana.

    availableSlots(Carbon $date, int $durationMinutes, ?Carbon $now = null)
        - Genera los slots "H:i" cada 30 min dentro de la ventana, descartando
          los que ya pasaron (cursor > now) y los que no dejan caber la
          duración completa (end <= close).

    hasConflict(int $workerId, Carbon $startsAt, int $durationMinutes, ?Appointment $ignore)
        - Busca citas activas del barbero en [startsAt-duration, end+duration]
          y detecta solape real [start, end) con la candidata.

    availableSlotsForWorker(int $workerId, Carbon $date, int $durationMinutes)
        - availableSlots() menos las horas con conflicto del barbero.
        - Es lo que consume el endpoint de availability y el flujo de agendar.

    busyBlocks(int $workerId, Carbon $date): Collection
        - Bloques ocupados [start, end] para el detalle.

5.5 FORM REQUESTS
--------------------------------------------------------------------------------
- StoreAppointmentRequest:
    worker_id: required|integer|exists:users,id (y el worker tiene rol
               worker/admin).
    date: required|date.
    time: required|date_format:H:i.
    services: required|array|min:1|max:10.
    services.*: integer|distinct|exists:services,id,active,1.
    withValidator(): revalida que la hora propuesta quepa dentro del horario
    (BusinessHoursService::isWithinHours) y que no haya conflicto con otras
    citas (hasConflict). Si no -> ValidationException.

    IMPORTANTE (Laravel 13): Rule::whereIn NO existe. En su lugar se usa
        Rule::exists('users', 'id')->whereIn('role', [Worker, Admin]).

- ProposeAppointmentRequest:
    starts_at: required|date_format:Y-m-d H:i:s|after:now.
    withValidator(): comprueba ventana de horario y ausencia de conflictos para
    la nueva hora propuesta.

- BusinessHourRequest: day_of_week required|integer|between:0,6, open_time y
  close_time required|date_format:H:i, active boolean. Valida open < close y
  que al menos un día esté activo si se desactiva uno (para no dejar la
  barbería sin agenda).

- BusinessHourOverrideRequest: date required|date, is_closed boolean, y si no
  está cerrado open_time/close_time required con open < close.

- RegisterRequest / LoginRequest / AddWorkerRequest / UpdateRoleWorkerRequest /
  UpdateActiveServiceRequest / SubscribePushRequest (ESTE ÚLTIMO ELIMINADO con
  el flujo de Web Push).

7. FLUJOS DE NEGOCIO
================================================================================

7.1 AGENDAR (solo rol user)
--------------------------------------------------------------------------------
1. AppointmentCreate carga services (activos), workers (worker+admin) y
   businessHours.
2. Paso 1: elige servicios (multi). Se muestra el total estimado
   (suma de precio y duración).
3. Paso 2: elige día (solo días con horario, respetando overrides) y hora.
   Cada vez que cambia día/barbero, se llama a GET appointments/availability
   con ?date=&worker_id=&services[]= y se muestran las horas libres reales.
4. Paso 3: elige barbero y envía el formulario (POST appointments/store).
5. El backend valida de nuevo horario y conflicto (StoreAppointmentRequest).
6. Se notifica al barbero y se redirige al detalle con flash success.

7.2 NEGOCIACIÓN (barbero -> cliente y viceversa)
--------------------------------------------------------------------------------
- pending: el barbero puede confirmar / rechazar / proponer hora.
- proposed: el cliente (y el barbero) puede confirmar (adopta la hora
  propuesta) / rechazar / proponer a su vez.
- confirmed: cualquiera de las dos partes puede cancelar (si es futura).
- Toda acción dispara una notificación al otro lado y un flash.

7.3 HORARIOS (admin)
--------------------------------------------------------------------------------
- Horario semanal: activar días y definir open/close por día.
- Excepciones: una fecha concreta puede estar cerrada o tener horario propio.
- Las excepciones tienen prioridad sobre el semanal (se corrigió el bug del
  cast de fecha).

8. BUGS REALES ENCONTRADOS Y CORREGIDOS
================================================================================

1. Rule::whereIn no existe (Laravel 13)
   Se usaba Rule::whereIn('role', [...]) en StoreAppointmentRequest y el test
   de validación fallaba. Se sustituyó por:
       Rule::exists('users', 'id')->whereIn('role', [UserRoles::Worker->value, UserRoles::Admin->value])
   (esto es un fallo real de la app: la validación del worker nunca funcionaba).

2. Tipo de retorno de Appointment::effectiveStart()
   El app usa Date::use(CarbonImmutable::class); el método devolvía
   Illuminate\Support\Carbon (mutable) y en algunos caminos retornaba
   CarbonImmutable -> TypeError. Se cambió la firma a
   `: Carbon\CarbonInterface` (interfaz común).

3. UserFactory sin 'phone'
   La columna phone es NOT NULL y unique; el factory no la generaba y los
   tests (y seeders) explotaban con violación de unicidad/null. Se añadió
   `'phone' => fake()->unique()->e164PhoneNumber()` (o similar).

4. Modelo Service sin HasFactory
   Service::factory() no existía; se añadió el trait HasFactory.

5. BusinessHourOverride: cast de fecha y prioridad de excepciones (BIG)
   El cast 'date' => 'date' guarda el valor como "Y-m-d H:i:s". En SQLite
   (base de tests) el where('date', '2026-08-21') NO coincidía, por lo que:
     - El test de cierre fallaba al hacer firstOrFail.
     - La excepción con horario especial NO tenía prioridad: se devolvían los
       slots semanales (09:00) en lugar de los del override (14:00).
   Se cambió el cast a 'date:Y-m-d', que guarda la fecha como "Y-m-d" y hace
   que la comparación con toDateString() funcione en SQLite y MySQL.
   Esto restaura la prioridad de las excepciones sobre el horario semanal.

6. Asserts de tests con decimales
   total_price con cast decimal:2 devuelve string ("150.50"), no float.
   Se ajustó la aserción del test a toBe('150.50').

7. Inertia v3: setData(key, callback) no acepta callback
   En AppointmentCreate se usaba setData('time', (d) => ...); Inertia v3 solo
   acepta el valor directo. Se reescribió para calcular el valor desde `data`.

8. HeroUI v3 API de Modal/Button
   ProposeTimeModal: se migró a useOverlayState() + state={state} + onPress;
   los botones usan isDisabled/aria-label en lugar de disabled/title.

9. Notificaciones: route() descarta parámetros no escalares (Laravel 13)
   En tests, route('notifications.latest', ['after' => $carbon]) perdía el
   parámetro por ser objeto Carbon. Se pasa la fecha formateada a string.

10. ESLint con ziggy.js
    resources/js/ziggy.js es generado; se añadió a ignore en eslint.config.js
    para no romper el lint en cada build.

11. Hora mostrada de la cita incorrecta (bug de zona horaria)
    Laravel 13 serializa las fechas con toJSON(), que añade el offset de UTC
    (ej. "2026-08-21T11:30:00Z"). El frontend formateaba en la zona horaria
    del navegador, así que una cita agendada a las 11:30 se mostraba a las
    4/5 (desplazada por el offset del navegador).
    FIX: se sobrescribió serializeDate() en Appointment (formato "Y-m-d H:i:s")
    y en BusinessHourOverride (formato "Y-m-d"), serializando la hora de muro
    sin zona horaria. El frontend la interpreta como hora local y muestra la
    hora correcta. También se formatea created_at de las notificaciones en
    HandleInertiaRequests con el mismo criterio.

12. Modal "Proponer hora": botones desbordados
    La estructura HeroUI v3 era incorrecta: Modal.Body y Modal.Footer estaban
    anidados dentro de Modal.Header, y los dos botones usaban w-full en una
    fila (se desbordaban).
    FIX: se reestructuró a Modal.Backdrop + Modal.Container (size="md") +
    Modal.Dialog con Header/Body/Footer como hermanos, y los botones del
    footer pasaron a flex-1 para que quepan en una sola fila.

13. Apagar un día de la semana no persistía
    DayRow siempre enviaba POST a business-hours.store, cuya validación
    marca day_of_week como único. Una vez que la fila existía, guardar de
    nuevo fallaba la validación (en silencio) y el día seguía apareciendo
    prendido.
    FIX: DayRow ahora usa la ruta business-hours.update (PUT) cuando la fila
    ya existe y business-hours.store (POST) solo para crearla. Además se
    muestran los errores de validación (day_of_week) debajo de la fila.

14. Orden de selección en el agendado (día -> hora -> barbero) + hora 12h
    - Antes la hora dependía de elegir primero el barbero (paso 3), por lo
      que los slots de hora nunca se mostraban en el paso "Día y hora".
    - Se hizo worker_id opcional en el endpoint de availability: sin barbero
      devuelve la unión de horas del negocio (availableSlots); con barbero,
      las horas libres de ese barbero (availableSlotsForWorker).
    - El paso 2 "Día y hora" ahora carga y deja seleccionar la hora sin
      barbero; el paso 3 "Barbero" verifica que la hora elegida siga libre
      para ese barbero y avisa (con mensaje ámbar) si no lo está.
    - Las horas se muestran en formato 12h: "13:30" -> "1:30 PM"
      (helper formatSlotTime para slots y formatTime en 12h para el resto de
      la app: tarjetas, detalle y modal de proponer hora).
    - Se añadió el test "la disponibilidad sin barbero usa solo el horario
      del negocio". Suite final: 24 tests, 24 pass.
